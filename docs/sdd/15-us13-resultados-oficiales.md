# US-13 — Registro de resultados oficiales

## Alcance y decisiones aprobadas

Un coach con cuenta `ACTIVO` y token Bearer puede registrar, consultar, completar y confirmar el resultado de una competencia de su equipo. El coach responsable se obtiene mediante `StudyGroupService`; el equipo se deriva exclusivamente de `Competition.group`. No se acepta un coach ni un equipo enviados por el cliente como autorización.

La competencia existente identifica la participación; se crea con `POST /api/competitions` (contrato en `03-api-contracts.md`), que permite registrar también eventos pasados con `status: FINALIZADA`. Al registrar este resultado, el coach declara su carácter oficial; no se añade una bandera a `competencia`, un catálogo externo de eventos ni un proceso de verificación externo. Los resultados son datos declarados por el coach, no una suma de `ProblemResolution`. US-11 y US-12 siguen utilizando las resoluciones individuales sin cambios.

Campos del resultado:

- `finalPosition`: entero de 32 bits mayor que cero.
- `solvedProblems`: entero de 32 bits no negativo; cero es válido.
- `confirm`: booleano explícito para confirmar; omitido equivale a `false`. `null`, cadenas y números no se aceptan como booleanos. Los campos numéricos no admiten cadenas, decimales ni truncado.

No se infieren puntajes, penalizaciones, evidencia, cantidad máxima de problemas ni posición a partir de envíos individuales. No se exige que los problemas oficiales estén cargados en el catálogo local.

## Estados y conservación

- `PENDIENTE`: admite información parcial, incluso ambos campos ausentes. Los valores proporcionados deben ser válidos. Puede registrarse antes de que la competencia finalice. El coach responsable puede consultar el detalle y reemplazar los datos pendientes mediante PUT.
- `CONFIRMADO`: exige ambos campos válidos, `confirm: true` y una competencia `FINALIZADA`. La confirmación es manual y la realiza el coach responsable. Se conserva la fecha de registro y se asigna la fecha de confirmación en UTC.

PUT reemplaza los campos editables completos; debe reenviar los valores que desea conservar. Omitir un campo lo deja `null`, permitido únicamente mientras siga pendiente. No es PATCH. Completar los campos sin `confirm: true` mantiene el resultado pendiente. Un resultado confirmado no puede modificarse ni volver a pendiente.

El historial competitivo contiene exclusivamente confirmados del equipo solicitado, ordenados por fecha de fin de competencia descendente y, en igualdad, ID de competencia descendente. Los pendientes no aparecen en el historial. El acceso al detalle y al historial está restringido al coach responsable activo; no hay publicación anónima ni acceso añadido para practicantes. Un historial vacío devuelve `200 []`.

La validación ocurre antes de modificar una entidad. Las escrituras son transaccionales; los errores revierten la operación y conservan el registro válido anterior. La actualización bloquea la fila pendiente con `PESSIMISTIC_WRITE`: una confirmación concurrente no puede sobrescribir otra ya confirmada. No se implementan versiones del resultado, eliminación, corrección de confirmados ni historial de cambios.

## Duplicados y límites del modelo

Existe como máximo un resultado por `competitionId`, pendiente o confirmado. POST duplicado devuelve `409`; para completar un pendiente se utiliza PUT. La restricción única de PostgreSQL protege también las creaciones concurrentes; se reconoce su nombre con `ConstraintViolations`, sin depender del idioma del servidor.

**Limitación aprobada:** si una misma competencia real se registra con identificadores de competencia distintos, US-13 no reconoce esa equivalencia. El modelo no dispone de identificador oficial de evento/edición y no se inventa una regla por nombre o fecha. Por tanto, esos registros se consideran participaciones distintas.

## Persistencia

`competitions.officialresult.OfficialResult` agrega la extensión autorizada `resultado_oficial_competencia`. No modifica entidades compartidas ni las tablas de US-11/US-12. El ERD gráfico permanece intacto; esta extensión está documentada también en `04-database-model.md` y en las expectativas de esquema.

DDL equivalente para aplicación manual en un entorno sin generación JPA:

```sql
CREATE TABLE resultado_oficial_competencia (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    competencia_id INTEGER NOT NULL REFERENCES competencia(id),
    posicion_final INTEGER,
    problemas_resueltos INTEGER,
    estado VARCHAR(20) NOT NULL,
    registrado_en TIMESTAMPTZ NOT NULL,
    confirmado_en TIMESTAMPTZ,
    CONSTRAINT uq_resultado_oficial_competencia UNIQUE (competencia_id),
    CONSTRAINT ck_resultado_oficial_valido CHECK (
        (posicion_final IS NULL OR posicion_final > 0)
        AND (problemas_resueltos IS NULL OR problemas_resueltos >= 0)
        AND (
            (estado = 'PENDIENTE' AND confirmado_en IS NULL)
            OR (estado = 'CONFIRMADO' AND posicion_final IS NOT NULL
                AND problemas_resueltos IS NOT NULL AND confirmado_en IS NOT NULL)
        )
    )
);
```

No hay cascadas hacia competencias o equipos, ni `grupo_id` redundante. La FK, la unicidad y los checks protegen los datos almacenados. La propiedad del equipo y el estado `FINALIZADA` se verifican en el servicio. La configuración `ddl-auto=update` existente puede crear la tabla al arrancar; no se modificó la configuración ni se aplicó DDL a una base local o compartida durante esta entrega.

## Contrato HTTP

Todas las rutas incluyen el context path existente `/api`:

| Método y ruta | Comportamiento |
| --- | --- |
| `POST /api/competitions/{competitionId}/official-result` | Crea un pendiente o un confirmado; `201`. |
| `PUT /api/competitions/{competitionId}/official-result` | Reemplaza un pendiente y opcionalmente lo confirma; `200`. No crea registros. |
| `GET /api/competitions/{competitionId}/official-result` | Detalle, incluido un pendiente propio; `200`. |
| `GET /api/competitions/teams/{teamId}/official-results` | Historial de confirmados del equipo; `200`. |

Ejemplo de confirmación, válido tanto para POST como para PUT de un pendiente:

```json
{
  "finalPosition": 4,
  "solvedProblems": 3,
  "confirm": true
}
```

Respuesta:

```json
{
  "id": 10,
  "competitionId": 20,
  "teamId": 1,
  "eventName": "Competencia Prueba",
  "competitionEndsAt": "2026-10-01T18:00:00Z",
  "finalPosition": 4,
  "solvedProblems": 3,
  "status": "CONFIRMADO",
  "registeredAt": "2026-10-02T10:00:00Z",
  "confirmedAt": "2026-10-02T10:00:00Z"
}
```

Los errores utilizan `{ "message": "...", "errors": {} }`, sin resultados parciales ni detalles SQL. `400`: ID/body inválido, valores incorrectos o requisitos de confirmación incumplidos; `errors` identifica los campos del resultado afectados. `401`: token ausente o inválido. `403`: rol/cuenta/coach no autorizado. `404`: competencia, equipo o resultado inexistente. `409`: duplicado, intento de modificar confirmado o relación de equipo inconsistente. `503`: acceso a datos o transacción no disponible. `500`: error inesperado. Corregidos los campos o recuperada la disponibilidad, el coach puede repetir la solicitud.

## Pruebas

`OfficialResultServiceTests` cubre registro, pendientes, confirmación, preservación ante errores, duplicados incluidos errores de unicidad concurrentes, autorización y separación por equipo. `OfficialResultControllerTests` comprueba contratos HTTP, tipos JSON estrictos y errores. `OfficialResultIntegrationTests` comprueba login real, persistencia, historial, integridad SQL y concurrencia en un schema PostgreSQL aislado.

La integración requiere `OFFICIAL_RESULT_TEST_DB_URL`, `OFFICIAL_RESULT_TEST_DB_USER` y, si corresponde, `OFFICIAL_RESULT_TEST_DB_PASSWORD`, con permisos para crear/eliminar schemas. Sin URL se omite. Comandos: [tests/README.md](../../tests/README.md).
